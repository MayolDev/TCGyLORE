## 2024-05-15 - Optimize O(N) memory allocation with relation mapping
**Learning:** In the DashboardController, the card distribution calculation loaded all `Card` models into memory and grouped them in PHP (`O(N)`). While `O(N)` queries might not seem slow early in a project, it's a critical memory bottleneck waiting to happen when scaling a collection app. Additionally, the `Card` model has a naming conflict between the `rarity` column and the `rarity` relationship. Testing DB queries using SQLite when the schema migration (`2025_12_21_171052_update_cards_table_with_relations.php`) is incomplete (missing `rarity_id` column) causes QueryExceptions.
**Action:** When calculating grouped relations, replace in-memory PHP operations with `select(foreign_key, DB::raw('count(*) as count'))->groupBy(foreign_key)->with('relation')->get()`. This is `O(R)` where `R` is the unique keys (rarities), significantly improving memory usage. To extract shadowed relationships safely, use `$group->relationLoaded('rarity') && $group->getRelation('rarity') ? $group->getRelation('rarity')->name : 'Fallback'`. If a column is missing in SQLite testing schemas, mock the `Eloquent` models in the test to verify collection logic rather than mocking complex `DB` facade chains.
